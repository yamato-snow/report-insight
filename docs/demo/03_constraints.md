# 制約と意図的なスコープ外

ポートフォリオとして正直に開示する制約の一覧。「できていないこと」と「あえてやらないと決めたこと」を区別する。

## 制約（現状できていないこと）

| 項目 | 現状 | 補足 |
|---|---|---|
| **データはすべて架空** | クライアント（中堅ビルメンテナンス会社）は架空の想定。報告書100件は `scripts/synth.py` の合成データ（シード固定・再現可能） | 境界例・悪文・表記ゆれ・プロンプトインジェクション検体を意図的に混入し、正解ラベル付きで評価にも使う |
| **AWS 未デプロイ** | Terraform（network/ecs/rds/pipeline/observability + dev/prod環境）は書き上げて validate/fmt green だが、apply していない | 「動くものを検証してから土台」の順序判断で凍結中。ローカルは LocalStack で S3/SQS を同一コードのまま動かす |
| **SSO 未実装** | 認証は dev 用の利用者切替（`?uid=`）。認可はサービス層で強制済み | 認証だけを差し替えられるよう抽象点として設計（本番は SAML → セッションに置換）。「なんちゃってログイン画面」を作らない判断 |
| **HTTPS 化未対応** | ドメイン取得の判断待ち。Trivy の該当2件は暫定除外中（`terraform/.trivyignore`） | AWS 構築と同時に解消する計画 |
| **自動デプロイ未実装** | CI は lint/test/セキュリティスキャンまで。ECR push / ECS 更新は枠のみ | AWS apply 後に OIDC で実装予定 |

## 意図的なスコープ外（要件として切ったもの）

| 項目 | 理由 |
|---|---|
| 現場スタッフ向けの報告書投入画面 | 現場は既存の報告システムを使い続ける前提（要件定義 §スコープ）。本番は S3→SQS 連携で受ける |
| DLQ の管理画面 | 運用頻度が低く、CloudWatch アラート + Runbook（`docs/runbook.md`）で担保する方が総コストが低い |
| 検索のさらなる高速化 | 非機能要件「3秒以内に読み始められる」は実測 880〜2,302ms で達成済み。要件を超える最適化はしない |

## 面談での伝え方（例）

> データは架空で AWS は未デプロイです。ただし、どちらも「作れなかった」のではなく順序の判断です。
> インフラを先に作りかけて指摘を受け、動くものと品質の検証を先に終わらせる方針に是正しました。
> Terraform 一式と CI のセキュリティスキャンは実装済みなので、apply の判断が下りれば載せるだけの状態です。
