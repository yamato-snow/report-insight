# AIに任せた部分と人間が判断する部分

設計原則: **AIは提案とたたき台、確定は必ず人**。それを画面の文言だけでなくコードで強制している。

| 工程 | AIがやること | 人（またはシステム）が守ること | 実装根拠 |
|---|---|---|---|
| 分類 | 分類・緊急度・要約・確信度を提案 | 確信度 0.85 未満は自動確定させず「未分類（要確認）」で人間のキューへ。確定操作は人だけができ、監査ログに残る | `app/services/ingest.py`（CONFIDENCE_THRESHOLD）、`app/services/admin.py` `override_analysis` |
| 緊急通知 | 緊急度「高」を判定 | 通知の見落とし防止はシステム側（Webhook 即時送信・二重通知の抑止） | `app/services/ingest.py` → `app/infra/notify/` |
| 検索回答 | 権限内の報告書を根拠に回答文を生成 | **引用実在検証**: 回答中の report:番号 が検索結果に実在するものだけ通す。0件なら生成せず「該当なし」。判断の裏取りは人が引用リンクで行う | `app/services/search.py`（`_parse_citations` / 0件ショートサーキット） |
| 月次報告 | 所見の文章のたたき台だけ書く | **件数・統計はSQLの確定値**（AIに数字を書かせない）。編集・承認は人。承認後は編集不可（状態機械）。QAロールは承認不可 | `app/services/monthly.py`（SQL集計 → 文章化のみ委譲、`approve` / `_deny_qa_writes`） |
| 入力の保護 | — | AIに送る**前に** PII をマスキング。報告書に紛れた指示文（プロンプトインジェクション）は無視するようプロンプトで固定し、評価ハーネスで耐性を実測 | `app/infra/masking/pii.py`、`app/infra/llm/prompts.py`、`tests/llm_eval/` |
| 記録 | — | 分類の上書き・月次承認・検索は追記専用の監査ログに記録（書き換え・削除不可） | `app/services/admin.py` / `monthly.py` / `app/api/routers/search.py` |

## この分担にした理由（面談で話せる形）

1. **LLM は確率的コンポーネント**なので、間違えたときの被害が大きい箇所（数値・確定判断・権限）には置かない。
   数字はSQL、確定は人、認可はサービス層——AIの守備範囲を「文章の提案」に限定した
2. **確信度しきい値は「AIをどこまで信じるか」の調整弁**。0.85 は評価データセット150件での
   分類 accuracy 0.94 / 緊急度高 recall 1.00 という実測に基づく（`make eval` で再現可能）
3. **人の修正が資産になる**設計。キューでの確定結果は `scripts/export_corrections.py` で
   評価データに還流し、しきい値やプロンプトの改善に使う

## 実測値（実API・2026-07-18・PASS）

| 指標 | 値 |
|---|---|
| 分類 accuracy | 0.94 |
| 緊急度「高」recall | 1.00（見落としゼロ） |
| 検索 recall@8 | 1.00 |
| 引用実在率 | 1.00 |
| 忠実性（5点満点） | 5.00 |
| プロンプトインジェクション耐性 | OK（明示的に拒否） |
